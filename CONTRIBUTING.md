# Contributing

Thanks for looking. This document covers setup, the gate, and the handful of
conventions that are load-bearing.

## Setup

```sh
pnpm install
pnpm validate      # or: pnpm validate --fix
```

Node 22+ and pnpm 11+. That is the whole setup — there is no code generation
step to run first, because packages export TypeScript source directly.

## Running your working copy of the CLI

**From source** (fast — every edit is picked up on the next run, no build):

```sh
cd apps/maxstack
pnpm cli -- --help
```

**As a linked binary** (drive a scratch project from anywhere):

```sh
cd apps/maxstack
pnpm build && npm link
```

The linked binary runs the esbuild bundle, not the source, so re-run
`pnpm build` after each change. Use `which maxstack` to tell which one is
active: a path inside this repo means local.

Undo with `npm unlink -g maxstack && npm install -g maxstack`.

## Testing a runtime change inside a real project

Most user-visible defects live in the runtime (`apps/web` and the packages the
build bundles), and the honest way to test a fix is to watch it inside a project
generated by an installed CLI. Link the checkout rather than copying build
output over a global install:

```sh
maxstack runtime link "$PWD" ~/scratch-project
maxstack dev ~/scratch-project
maxstack runtime status ~/scratch-project     # which runtime resolves, and why
maxstack runtime unlink ~/scratch-project
```

## The gate

Nothing lands unless `pnpm validate` is green. It runs, in order: lint,
boundaries, write-paths, owned-writes, guarded-statements, client-safe-imports,
test-integrity, docs-reference, test-shards, typecheck, test.

`--skip=name,name` drops steps; an unknown name is a hard error, because a skip
list that silently matches nothing would quietly stop running a step while still
reporting green.

### Read the last line

A green gate proves the tree is good **on this machine**. CI runs on a Linux
runner, sharded, with no global `maxstack` on PATH and none of your environment,
so a test that reads the machine passes here and fails there. That is not
hypothetical: it once hid for fifteen consecutive commits, every one of them
behind a green local gate, because nobody was looking at CI.

So `pnpm validate` ends by printing how the last CI run on `origin/main` did.
It is a report, not a gate — it can never fail your run, and it degrades to a
dimmed "unknown" line when `gh` is missing or the network is not there. A red
line means open the URL before you push over it.

## Why the checks exist

They cost about half a second combined, and most of them exist because a
specific bug shipped green. That history is the argument for keeping them:

- **`check-guarded-statements`** — this repo omits semicolons, so a statement
  starting with `(` or `[` carries a leading `;`. Put that in the body of a
  braceless `if` and the formatter rewrites it into an `if` guarding an *empty*
  statement, with the expression below now running unconditionally. It formats,
  typechecks and lints clean. It shipped once, turning a guarded assertion into
  one that fired on every path — with the test still passing, for the wrong
  reason. Only reading the diff caught it, so this reads the diff mechanically.

- **`check-client-safe-imports`** — no route module may reach a compiler. The
  ownership barrel pulls in `ts-morph`, and React Router puts route modules in
  the client bundle. The page then server-renders correctly and does nothing
  afterwards. The production build tree-shakes it away, so *only* `pnpm dev` was
  broken, and only in the console.

- **`check-write-paths`** — every place that can land a spec op is declared and
  covered by an invariant test. It is an allowlist, so a new way to write the
  spec fails until somebody accounts for it.

- **`check-owned-writes`** — the filesystem half of the same idea, and it exists
  because the spec-op registry above could not have caught the bug. `maxstack add
  view` wrote its scaffold with a bare `fs.write`, so the one command whose output
  is stamped `THIS FILE IS YOURS` was also the one command that silently
  overwrote it, and then re-flipped the manifest entry it had itself set to
  `ejected`. It touched no op, so nothing was watching; the existing suite ran the
  verb three times and never noticed. An unattributed op is at least logged and
  revertible — an overwritten ejected module is gone. So a destructive write into
  a project's app tree, whether through the `Fs` port or `node:fs`, must come
  from `packages/maxstack-core/src/ownership/` or be declared in
  `scripts/owned-writes.config.json`. The registry exempts a **target
  expression**, never a file: `commands/view.ts` may write the manifest and
  nothing else, so the exact line the fix removed is still a failure today.

- **`check-boundaries`** — the layering in [ARCHITECTURE.md](ARCHITECTURE.md),
  enforced. Remediate by moving code down the stack or extracting the shared
  piece — changing the policy file is a last resort and belongs in its own
  commit explaining the new direction, never a drive-by to make a branch pass.

- **`check-test-integrity`** — see below.

Two more need a build, so they run in CI's `smoke` job rather than in `validate`
(nothing in `validate` emits a bundle, so neither failure is visible to it):

- **`check-chunk-cycles`** — a cycle between emitted chunks makes initialization
  order decide whether a module-level binding is defined when another chunk
  reads it. That is a boot crash, for code that passed every test.

- **`check-payload-budget`** — `maxstack-runtime` ships `apps/web/build`
  verbatim, and 87% of a cold start is the download, so payload size is a
  latency number. It grew 22.9MB → 41.5MB unnoticed, and 16.8MB of that was
  three files *nothing referenced*: the client build walked into
  `@electric-sql/pglite`, emitted its wasm and data assets, then tree-shook away
  every chunk that could name them. So the check has two halves — a total under
  budget, and zero unreferenced assets, the second being the one that names the
  class instead of the instance. Run it yourself with
  `pnpm --filter @maxstack/web build && pnpm check:payload-budget`.

## Test integrity

Never make a gate pass by weakening it: no deleting, skipping or loosening a
failing test, no drive-by lint or type suppressions, no relaxing validate or a
CI step inside a feature change. If a test or gate is genuinely wrong, it changes
in **its own commit, with the reasoning**.

`pnpm check:test-integrity` enforces this. Skipped tests, focused tests,
swallowed exit codes, non-failing CI steps and typechecker suppressions are all
held at zero; lint suppressions are a ratchet that may only go down. If you
genuinely need an exception, argue it in review — do not raise the ceiling to
accommodate a new suppression, which is how a ratchet becomes decoration.

## Conventions

- **Formatting**: Biome — tabs, single quotes, no semicolons, trailing commas.
  `pnpm lint:fix`.
- **Commit subjects**: Conventional Commits. This is load-bearing —
  `CHANGELOG.md` is generated from them.
- **TypeScript**: `strict`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`.
- **Comments**: put the *why* next to the thing it explains, especially when you
  fix something subtle. A comment saying what breaks without a check is worth
  more than a document nobody finds.

## Adding a spec-op

1. Add the op to the vocabulary in `packages/spec/src/base/spec-ops.ts`, with
   validation (references resolve, ids fresh) and an immutable apply.
2. Thread any new field through the codec so it survives a round trip to disk.
3. Add it to the generator that consumes it.
4. Regenerate the reference docs: `pnpm docs:reference`. The drift check in
   `validate` fails any change that adds an op without documenting it.

## Adding a feature bundle

Bundles live in `packages/features/src/bundle/`. A bundle contributes spec ops,
optional runtime DDL, and seeds, and declares its prerequisites. Add it to the
catalog, give it a version, and note that bundle combinations are gate-checked —
adding one grows the combination lattice.

## Reporting a security issue

See [SECURITY.md](SECURITY.md). Please do not open a public issue for a
vulnerability.
